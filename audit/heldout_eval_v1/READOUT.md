# 冻结新材料的真实模型对照：结果与限制

6 份冻结的新模拟材料分别执行一次完整两步 Workflow、一次直接 review，共 12 次运行、18 个真实 Ollama 模型步骤。12 次运行均返回可解析 JSON 并在程序层 completed，但业务正确性明显不足。加入状态、精确规则覆盖、引用和材料要求后，两种方式都只有 H05 一例满足本批检查；本批不能支持“多一步提取就更可靠”的结论。

## 方案与控制读回

- 模型：`qwen3:4b-instruct-2507-q4_K_M`；provider=`ollama`，没有 mock 或失败回退。
- 同一 `server.py`，独立临时 SQLite 和本机空闲端口 60988；未使用主数据库或主服务。
- 两步组：原文提取 → review；直接组：相同 review Skill，`extraction={"items":[]}`。
- 两组 document/context/rules 完全一致，review 的 instructions/output_requirements 完全一致。运行后逐个核对 12 份记录；两步组 review 输入中的 extraction 等于第一步完整输出。
- 固定参数：temperature=0.1、num_ctx=8192、num_predict=2048、timeout=180秒。每例只执行一次，每例交替两组先后顺序；没有根据结果改 prompt、调参数或重试。
- 使用 `audit/pre_role_fix_starter.json`，不受随后默认 Workflow 政策绑定调整影响。冻结 fixture 与该快照的身份读回一致；未改 expected。
- 总用时 115.827 秒。两步组各例用时中位数 10.357 秒，直接组 8.957 秒，仅作本轮运行记录，不作性能基准。

## 机器检查

规则覆盖要求每个所选 rule_id 恰好一项、不能多出或变更。逐状态按预期 rule_id 匹配，错误键名和变更 ID 不做容错归一化。非空 quote 必须为原文连续子串；这只检查引用保真，不检查引用是否足以支持该项理由。

| 检查 | 两步 Workflow | 直接 review |
|---|---:|---:|
| 程序 completed | 6/6 | 6/6 |
| 预期规则状态命中 | 20/27 | 18/27 |
| 精确规则 ID 覆盖 | 4/6 | 4/6 |
| 最终 review 引用全部逐字来自原文 | 5/6 | 6/6 |
| 上述机器检查共同通过 | 2/6 | 1/6 |
| 加入逐例阅读的材料要求检查后共同通过 | 1/6 | 1/6 |

两步组第一步提取的非空 quote 在 6 例中均为原文子串，但存在类型误分，例如把“产品资料现已开放查阅”标为收益；不能把引用保真等同提取业务正确。

## 评分器修正披露

保留了未修正的 `results_initial_grader.json`。初版评分器遇到某一 check 缺 rule_id 时丢弃整组，错误把 H04 直接组计为 0/5 且引用失败。修正后保留其余有效项、单列无效项：H04 直接组为 2/5，引用逐字检查通过，精确覆盖仍失败。该修正只重新读取已保存原始 JSON，没有改模型输出、fixture 或预期，也没有重跑模型。

## 有限结论与后续优先项

真实两步数据传递已经验证，两个组的输出也确实不同。当前提取步骤在 H03 的状态识别上表现较好，但 H02 引入错误引用；最终共同检查通过例数相同。单次 6 例合成材料、单一小模型、无重复采样，不能据此声称两步统计优于或劣于直接 review，也不能把 20/27 与 18/27 当总体准确率。

若继续做下一版本，优先增加精确 rule_id/引用的确定性校验、对“适用条件不满足却 needs_material”的状态矛盾提示，以及结合渠道和已提供背景核对材料要求。下一版本应使用独立验证并保留本次失败结果，不能覆盖本批 expected 后重新报通过。
