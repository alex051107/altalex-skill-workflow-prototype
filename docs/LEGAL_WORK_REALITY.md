# 先把法律人员的工作想清楚，再决定 Skill 与 Workflow

2026-10-21。本文是本轮业务反思与产品决定，不是客户访谈记录。依据包括正式考题、具名法律人员的公开实践、监管机构的企业实践调研、竞品官方操作说明，以及获授权测试账号内的实际操作。法律业务类型不同，以下以营销材料预审为主；合同谈判与律所尽调只作对照。不能从总部在新加坡推定客户和适用法域。

**当前判断：考题要求把业务人员反复依赖法律专家完成的方法，变成可以自助配置、测试、复用和检查的产品。现有原型证明了执行框架；它只覆盖一次预审工作的中间部分，还没有证明真实法律人员愿意用、能够独立配置，或审阅质量已达到业务要求。**

## 1. 原来理解得不够深的地方

我原来按“提取 → 审阅 → 生成草稿”拆步骤，首先考虑了模型怎么调用。法律人员首先要弄清：是谁要求做什么、商业目的是什么、材料是否完整、用哪套标准、意见给谁、谁能决定例外，以及哪版内容最终被采用。一个步骤多的流程，并不自然等于一次工作完成。

还有三个不成立的默认假设：不是每位律师都应从空白编写字段和 JSON；不是每个使用者都应每次提供政策；也不是模型说“缺材料”就已经完成有价值的分流。如果背景已经回答过问题，仍然索要同一信息，会给法务和业务增加工作。

因此，当前更合理的首轮目标是：**帮助法务形成一份可核查、可继续处理的首轮预审意见，并把经过确认的方法留给下一次使用。** 不把系统定位成替代完整的发布审核或自动法律决定。

## 3. 营销预审：从一个具体请求还原工作

下面是为本题构造的工作走读，不是真人案例：市场准备发布一则静态图文，含“最高 8% 收益”和“不是广告”，实际是付费委托，只有文字，没有最终图片和计算依据。

| 工作时刻 | 法律人员需要弄清的事 | 应留下的工作产物 | 当前原型覆盖 |
|---|---|---|---|
| 接到请求 | 哪个业务／产品、面对谁、在哪里和什么渠道发布、希望何时完成、谁负责补件；是新材料还是改稿 | 任务背景与材料版本、明确的审阅范围 | 可填写 context；尚无结构化事项与版本关联 |
| 清点事实和材料 | 文案、最终图片是否齐全；8%是谁计算、口径是什么；推广关系已经确认还是未知 | 已知事实、缺项及其提供人；已有材料不重复索取 | 有缺材料输出，但新样例暴露重复索要及类型错误 |
| 选定方法 | 哪些公司政策已经确认适用；哪些问题需要额外法律研究；是否有有效例外 | 本次选定规则及版本、适用依据、例外依据 | 规则可固定并随运行留快照；适用确认及例外并无专门交互 |
| 对照审阅 | 每个问题对应哪句、哪份依据；是事实不足还是已显示偏离；是否影响本次目的 | 带位置和依据的意见；区分问题、缺材料、不适用和待确认 | 已有卡片与引用检查；覆盖和语义质量不足 |
| 交回业务处理 | 哪处文字需要改、谁补什么材料、哪些问题需法律人员决定 | 可执行的修改／补件事项与清晰接收对象 | 仅生成补材料草稿；R2 的文案问题没有因此解决 |
| 收到新版本 | 改了哪里，先前意见是否解决，是否引入新问题；最终版是否就是审过的那版 | 未结项清单、修订比对与复核意见 | 可以另跑新材料，但不追踪同一事项和意见关闭 |
| 形成决定并留档 | 按组织制度由谁决定什么，哪些条件仍成立、对应哪版材料 | 人的决定、依据、材料和适用条件 | 没有正式签批或发布记录，模型完成不能替代它 |

这张表的最后三行说明为什么“再接一个生成邮件的 Skill”不等于业务闭环。对 MVP 可以有意识地只做到首轮预审意见，但必须说清后续交给谁，不能把剩余工作藏在“人工复核”四个字里。

## 4. 三种角色需要分清

**规则所有者**决定公司希望坚持什么、允许何种退让、哪些例外需谁决定。它可能是资深法务或某个专业负责人，不能让历史改稿或模型建议自动成为公司政策。

**方法配置者**把该方法转成任务说明、输入、输出和测试。可能是同一名律师，也可能是法律运营、知识管理或熟悉工具的人与律师合作。当前界面的英文字段／JSON 要求更接近后者；尚不能宣传成所有律师都能零帮助使用。

**具体事项处理者／材料提供者**使用已确认的方法。公司里可能是法务自己、初级法务，或通过受限入口提交材料的市场人员；律所里也可能是律师团队。我们暂按“法务配置、市场提供材料、法务核查”演示，真正首批用户仍需确认。

方法创建的过程应当是：拿一份实际检查清单与代表材料 → 讲清适用范围和例外 → 配置可复用任务 → 在有预期结果的样例上试用 → 修正 → 由有责任的人决定是否供团队使用 → 根据使用反馈维护。当前只实现其中配置、测试、保存和运行的部分。

## 6. REA 应当验证业务边界

REA 的用途是验证已经交付给浏览器的界面和参数如何组织，不是通过前端猜出公司内部产品战略。

| 业务问题 | 当前证据 | 能得出的结论 |
|---|---|---|
| 尽调范围由谁确认 | 已定位清单生成／编辑／选择路径；真实 UI 取消全部后不能继续，选 3 项后可执行 | 中间确认确实存在；报告仍出现范围外事项，选择清单不保证下游严格遵守 |
| Library 和 Project 是否仅名称不同 | 两个入口脚本共用 workspace／folder 组织；实际可创建资料区并上传 | 支持共享前端组织；不证明后端权限相同，也不证明完整事务管理 |
| 存入政策能否被准确取回 | Library 查询 P1 首选 12 个月、退让 6 个月且需法务批准，点击引用显示原页 | 这一例资料问答可用；不证明政策自动变成可复用审阅 Skill |
| 页面中的 skill 一定是题目中的自建能力吗 | 共用上传代码将可选 skill 传入上传参数，又将同一值作为 schema_name 传入编译任务 | 此处与文件处理配置有关；不足以证明题目要求的任务说明、输入输出、测试保存和跨材料组合能力已经存在 |

本轮 REA 对 Library／Project 两个入口和共用资料处理脚本做定向静态分析；实时 CDP 在列出目标后发生连接问题，后续 UI 测试由 Computer Use 完成。不能将没有成功的实时捕获说成已抓到接口请求。完整来源记录在研究档案，交付包不包含生产脚本或调试连接信息。

## 7. 本轮决定及优先顺序

**已经落实：** 政策由创建者保存在 Workflow，操作人员只交文案与背景；未知字段来源默认留空；测试草稿明确未保存并能返回继续修改；第三步改名为补材料草稿。这些改动服务于责任和操作清晰，而非增加模型复杂度。

**质量没有过关：** 6 例预先冻结的新材料，12 次真实运行都完成，但两步与直接审阅在状态、规则覆盖、引用和具体材料要求联合检查下各只有 1/6 符合。规则遗漏、误解已知背景和错误补件会增加法律人员的工作。详见 [原始结果与方法边界](../audit/heldout_eval_v1/READOUT.md)。这是合成材料与 AI 辅助逐例阅读，没有律师审阅。

**下一次迭代先做三个决定：**

1. 确认首个用户和事项：由一位实际维护规则的人与一位处理材料的人，共同走读一件脱敏案例；决定原型止于首轮预审还是必须支持补件后复核。
2. 确认“可用意见”标准：必须覆盖哪些规则，什么证据足以支持什么结论，什么情况停止或升级。再据此增加可配置的覆盖／引用校验与材料类型检查，使用新样例验证，保留本轮失败。
3. 确认自助维护成本：让未参与开发的人按普通业务描述建一个新 Skill、测试并加入流程；记录帮助次数、错误绑定、修改难点。依据结果决定优先提供模板／辅助生成／业务字段，不能只演示开发者熟练操作。

暂不扩展更多法律场景、更多 Agent 或企业级大系统。根据一次工作中最耗时、最容易错、责任最不清的交接点来选择下一项能力。

## 8. 面试时可以这样讲

“我先区分了团队方法的创建者和每次事务的处理者。真实审阅不仅是读文字，还要确认背景、适用规则、证据和例外，再把意见交回去修改或补材料。我用营销材料预审验证其中一段，交付带原文和规则依据的首轮意见。试用 AltaLex 发现资料库已经能做带来源问答，尽调也有中间清单确认，所以新增价值应是让客户把自己的方法保存、测试和复用。我修正了让操作人员每次复制政策的问题；同时保留六例新材料的失败，说明目前模型质量还没达到可靠业务使用。下一步会先让真实法务走读案例和独立配置，再决定需要怎样的审批或补件功能。”

## 9. 一次具体走读只问五件事

1. 请打开最近一次从初稿到最终处理的脱敏材料：最初谁提出什么请求，最终交了什么？——决定真正的输入与交付边界。
2. 哪一步必须补问，什么事实改变了意见？——决定必填背景、材料清单和是否需要暂停。
3. 检查依据从哪里来，谁能改，过去的例外能否再次使用？——决定规则归属、来源、版本和例外处理。
4. 哪些问题必须交别人决定，改稿后如何确认已解决？——决定分工、复核和事项状态。
5. 如果给你现有原型，哪一份输出你会保留，哪一份会重做？——用实际接受和返工检验价值，而非仅问“觉得怎么样”。

这些是已准备但尚未开展的访谈问题；没有代用户向 HR 或任何法律人员发送。
